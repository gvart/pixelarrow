# ADR-0009: Linked accounts, display names and account deletion

## Status
Proposed

## Date
2026-10-13

## Last Verified
2026-10-13

## Decision Makers
Autonomous v6 run, story P2-ARCH-ACCT (roles: security-engineer with network-programmer). The Director accepts or sends back.

## Summary
v6 lets one player sign in with Telegram, email and password, or both (brief Goal 6). It needs a public nickname that is not Telegram personal data (V6-011), and an in-app deletion that the privacy notice can promise (Goal 9). This ADR keeps one `players.id` per person and adds log-in methods only with two-sided proof. It never merges game state: when both sides have progress, the player picks one account to keep and the other is deleted. Display names are validated and unique, generated by default, and moderated by admins. Deletion removes all personal and gameplay data, keeps an anonymised tombstone for legal bookkeeping, and frees the Telegram id and the email.

## Context

### Problem Statement
- **Linking:** without it, a Telegram player can't continue on the web, and a web player can't bring their account into Telegram. Two accounts with progress can't be safely merged: about 45 game tables hold heroes, items, wallets, ratings, regions and clans, and a merge invites duplicated resources and broken invariants (one live duel profile per player, one region garrison per hero).
- **Names:** public boards show `first_name`, `username` or `Player <telegram_id>`, which is Telegram personal data on an unauthenticated API (V6-011).
- **Deletion:** `/delete_my_data` only files a support ticket. The privacy notice can't promise deletion until there is a real, complete path.

### Constraints
- Telegram proof exists only inside the Mini App (`initData`) unless the bot's domain is set up for the Login Widget.
- Stars purchases are tied to a player and are non-refundable in-game goods (refund policy); they must never silently vanish through a link flow.
- No live users (V5-074).

### Requirements
- One player id, several log-in methods, at most one of each kind.
- Link in both directions; unlink without ever stranding an account.
- A clear rule when both sides have progress.
- A unique, validated nickname everywhere public.
- Self-service deletion with a defined list of what is deleted, what is kept and why.

## Decision

### 1. One player, several identities
`auth_identities` (ADR-0008) holds at most one `telegram` and one `password` row per player. Log-in with either one resolves to the same `players.id`. Every sensitive action below needs **re-auth**: `sessions.reauth_at` within the last **10 minutes**, set by:
- a password log-in, or `POST /api/account/reauth {password}`, for an email identity
- a fresh `initData` with `auth_date` at most 10 minutes old, via `POST /api/account/reauth {initData}`, for a Telegram identity

Sensitive actions: link, unlink, change email, change password (it already asks for the current password), resolve a conflict, and delete the account.

### 2. Telegram player adds email and password (Telegram → web)
1. In the Mini App (bearer session, re-auth), the player posts `POST /api/account/email {email, password}`. There's no Turnstile here, because the iframe can't run it reliably and the caller is already authenticated. The per-account limit is 5 requests per hour (`auth_throttle` key `addmail:<pid>`), plus the mail caps from ADR-0008.
2. The server stores `email_tokens(purpose='add_email', player_id, pending_hash)` with a 24 h TTL and emails a link. If the address already belongs to an account, the response is the same `202`, and that mailbox gets an email that says so (see conflicts).
3. The link opens `play.pixelarrow.app/auth/add_email#t=…`, which can be in any browser. `POST /api/auth/verify` inserts the `password` identity and its hash for `player_id`, then issues a web cookie session there. The player is now signed in on the web, and the Telegram side is unchanged.
4. A confirmation email goes to the address, and a bot message goes to the Telegram chat ("Email added to your pixelarrow account. Not you? Open Settings → Account").

### 3. Web player links Telegram (web → Telegram)
1. On the web (cookie session, re-auth), `POST /api/account/link/telegram` returns a **link code**: 16 random bytes, stored hashed in `link_codes` with a 10-minute TTL, single use, and bound to the player. The client opens `https://t.me/<bot>/<app>?startapp=link_<code>`.
2. The Mini App starts. Its `initData` carries `start_param`, which Telegram signs. The client shows **"Link this Telegram account to pixelarrow account `<display name>` (`j***@g***.com`)?"**, fetched with `GET /api/account/link/telegram/:code`, which returns only that name and masked email.
3. On "Link", the client posts `POST /api/account/link/telegram/complete {initData}`. The server checks:
   - the `initData` HMAC, with `auth_date` at most 10 minutes old
   - that `start_param` equals `link_<code>`
   - that the code is valid and unused

   It then records `link_codes.telegram_id` and sets `status='awaiting_web'`. Nothing is linked yet.
4. **Two-sided confirmation:** the web page polls `GET /api/account/link/telegram/status` every 3 s, for at most 10 minutes. It shows "Telegram account `@username` / `first name` wants to link. Confirm?". Only the web session that created the code can confirm, with `POST /api/account/link/telegram/confirm`, and the link happens then.

   Why both sides: a leaked or shoulder-surfed code alone can't attach an attacker's Telegram to a victim's account. A code sent by an attacker to a victim can't attach the victim's Telegram either, because the victim's web session never created it.
5. On confirm, in one D1 batch: insert the `telegram` identity, set the `players.telegram_id` mirror, and mark the code used. If that Telegram id already has its own player, the conflict rules in §5 apply first. The bot sends "Linked to your web account", and an email goes to the address.

The Telegram Login Widget is **not** used in v6. It needs BotFather `/setdomain` and a second validation scheme, and the Mini App path proves the same thing with the HMAC check that already exists. This is logged as a proposal.

### 4. Unlink
- `DELETE /api/account/identities/telegram` or `/password`, with re-auth. **Refused (`409 last_login_method`) if it would leave no identity.**
- **Unlink Telegram:**
  - Delete the identity, clear the `players.telegram_id` mirror, and delete `notify_settings`, `bot_state` and pending `notify_outbox` rows (the bot can no longer reach the player).
  - Revoke all `bearer` sessions.
  - Purchases and entitlements stay with the player: they belong to the player id, not the Telegram id.
  - If that Telegram user opens the Mini App again, they get a new, empty player.
  - Email notice.
- **Unlink email:** delete the identity and its hash, revoke all `cookie` sessions, and send an email notice to the old address.
- **Change email:** `POST /api/account/email/change {email}`, with re-auth, uses the `change_email` token sent to the **new** address. On verify, `subject` and `email` are swapped in place, and a notice goes to the **old** address with a "this wasn't me" link to reset.

### 5. Conflicts: both sides already exist
A conflict happens when linking Telegram `T` to web player `W` where `T` already owns player `P`, or when adding email `E` to Telegram player `P` where `E` already owns player `W`.

**There is no merge of game state, ever.** One account survives and the other is deleted (§7).

1. **The other side is empty → automatic.** "Empty" means: no cloud save with campaign progress beyond the first battle, no `online_profiles`, `duel_profiles` or `duel_ratings` row, no `purchases` or `entitlements`, a wallet balance of zero and no ledger entries other than starter grants, and no clan membership. Delete the empty player under §7 and attach the identity to the surviving one. No question is asked.
2. **Both have progress → the player chooses.**
   - For an email conflict, the player must also prove the other account. Clicking the verify link proves the mailbox, and they must also enter `W`'s password (or reset it first). Without that proof the flow stops with "this email belongs to another account".
   - The client shows both accounts side by side, from `GET /api/account/conflict/:id`: display name, campaign stage, hero count, duel rating, war season profile, purchases yes or no, and created date.
   - The player picks the survivor with `POST /api/account/conflict/:id/resolve {keep: 'this' | 'other', confirm: '<loser display name>'}`, typing the loser's display name to confirm.
   - The survivor gets both identities. The loser is deleted under §7, which revokes its sessions.
3. **Purchases decide the survivor.** An account with `purchases` or `entitlements` can't be the loser. If only one side has purchases, it must be the survivor, and the choice is preset with a reason. If both have purchases (impossible today, because the web has no payments yet), the flow refuses with `409 contact_support`, and support resolves it by hand.
4. **Not during live play.** If the loser is in a live duel match, the matchmaker queue, an open battle ticket or an active world-boss attempt, refuse with `409 busy_try_later`.
5. Conflict records (`link_conflicts`: id, `survivor_candidates`, `kind`, `created_at`, `expires_at` of 15 minutes) are short-lived and pruned daily.

### 6. Display names (V6-011)
- **Columns** (ADR-0008 §1): `display_name` and `display_name_key UNIQUE`. Migration 0018 adds:
  - `players.public_boards INTEGER NOT NULL DEFAULT 1` (the opt-out from public, landing-page boards)
  - `players.name_changed_at`
  - `players.name_locked_until`
  - a table `display_name_history (player_id, old, new, changed_at, by_admin)`
- **Default:** every new player gets a generated name, `<Adjective><Unit><4 digits>` (for example `SwiftArcher4821`), from curated word lists in English. **Never** the Telegram first name or username. The game's first run offers a rename.
- **Rules (`server/src/names/validate.ts`, shared with the client for instant feedback; the server is authoritative):**
  - NFKC, trim, and collapse inner whitespace.
  - Length 3–16 characters.
  - Allowed characters: Latin letters, Cyrillic letters, digits, single space, `_` and `-`, not at the start or end and not twice in a row. At least one letter.
  - **No mixing of Latin and Cyrillic letters in one name** (this stops homoglyph impersonation, for example a Cyrillic `а` in `admin`).
  - No `@`, no `.`, no URLs (they can't be typed with the allowed characters anyway).
  - `display_name_key` = the name lower-cased, with spaces, `_` and `-` removed, and common look-alike digits folded (`0→o`, `1→l`, `3→e`, `4→a`, `5→s`, `7→t`) before the uniqueness check, so `Adm1n` and `admin` collide.
  - **Reserved** (checked on the key): `admin`, `moderator`, `mod`, `support`, `system`, `official`, `pixelarrow`, `telegram`, `cloudflare`, `deletedplayer`, `hiddenplayer`, `null`, `undefined`, plus their Russian forms.
  - **Blocklist:** a small English and Russian list of slurs and sexual terms (`server/src/names/blocklist.ts`), matched as substrings of the key. It is kept in the repo, reviewed by the owner, and not shown to players. The rejection message is generic: "This name isn't allowed".
- **Changes:** `PUT /api/account/name {name}`, session required. The first change is free. After that, at most one change every 30 days, and none while `name_locked_until` is in the future. Every change is written to `display_name_history`. Names freed by a rename or a deletion are reserved for 30 days (checked through the history).
- **Moderation (admin):** `POST /api/admin/players/:id/rename` resets the player to a generated name, sets `name_locked_until` (7 days by default) and writes `admin_audit`. The admin player search also matches `display_name`. There is no player report button in v6 (a proposal).
- **Clan names** go through the same validator, character set and blocklist, with a 3–20 character length, from the same story. They are public on the war board (ADR-0010).
- **Where it is used:** every leaderboard, war standings, duel opponent cards, clan rosters, presence and the public API. `online/store.ts`'s name lookup and `players.displayName()` read `display_name` only. `first_name` and `username` are never sent to any client except the player's own `/api/me`.
- The session carries no name (ADR-0008), so a rename takes effect on the next request. Durable Objects get the name per connection, so it takes effect on reconnect.

### 7. Account deletion
- **Request:** `DELETE /api/account {confirm: 'DELETE'}`, with re-auth. The UI is Settings → Account → Delete account, with the privacy notice linked. It lists exactly what will be lost and warns in bold if the account has purchases ("paid items are lost and are not refunded; see Refunds").
  - The Mini App can trigger it too (re-auth by fresh `initData`).
  - The bot's `/delete_my_data` now replies with a button that opens Settings → Account, instead of filing a support row.
  - The same procedure runs for the loser of a §5 conflict.
- **Immediate and irreversible.** There is no grace period (simplest to reason about and to describe in the notice). A confirmation email is sent to the address, if there is one, before the identities are removed.
- **Procedure (`server/src/account/delete.ts`).** It is idempotent and resumable. `deletion_jobs(player_id PK, step, started_at, finished_at)` lets the daily cron finish a run that was interrupted (D1 batch size limits).
  1. Set `players.deleted_at`, and refuse if the player is busy (§5.4).
  2. **Revoke and free:** delete all `sessions`, `auth_identities` (cascading to `password_hashes`), `email_tokens`, `link_codes`, `link_conflicts`, `auth_throttle` keys for the player. The Telegram id and the email can now be used for a new account.
  3. **Leave shared structures:**
     - Remove the player's active `market_listings`. The escrowed items are deleted with the player, and buyers can no longer see the listings.
     - Release owned `online_regions` and garrisons, using the region rules for an abandoned region.
     - Leave the clan. A leader passes leadership to the oldest officer, then the oldest member. If the clan would be empty, it is disbanded.
     - Remove the player from `duel_queue_state` and `MatchmakerDO`, and tell the `RegionDO` and `DuelDO` to close the player's sockets.
  4. **Hard-delete** everything personal or gameplay-only, keyed by the player:
     - campaign and online: `saves`, `online_profiles`, `online_heroes`, `online_items`, `online_camps` (+ buildings), `online_consumables`, `consumable_daily`, `battle_tickets`, `merchant_daily`, `merchant_orders`, `loot_pity`
     - duels: `duel_profiles`, `duel_heroes`, `duel_items`, `duel_tickets`, `duel_orders`, `duel_loadouts`, `duel_ladder_stars`, `duel_ladder_chests`, `duel_defences`, `duel_ratings`
     - economy and bosses: `wallets`, `cosmetic_loadout`, `pass_progress`, `pass_claims`, `shop_orders`, `world_boss_chests`, `world_boss_loot`
     - notifications, support and telemetry: `notify_settings`, `notify_outbox`, `notify_log`, `bot_state` (player-keyed), `support_requests`, `analytics_milestones`, `client_errors` (rows with that pid), `display_name_history`
  5. **Keep, anonymised.** These rows stay pointing at the tombstone player id, with no personal data:
     - `purchases` and `entitlements`: the Telegram payment charge id, product, amount and dates are kept for tax and bookkeeping and for disputes. The retention period is set in the notice (the owner confirms it; proposed 5 years). The rows keep no name, username or Telegram id, only the tombstone `player_id`.
     - `drachmae_ledger` and `market_audit`: kept for the integrity of the economy audit, pseudonymous.
     - `admin_audit`: kept (moderation record).
     - Other players' history stays, shown as "Deleted player": `battle_log`, `duel_matches`, `duel_attacks`, `world_boss_damage`, `season_rewards`, `duel_season_rewards`.
  6. **Tombstone:** the `players` row stays, so the roughly 44 foreign keys hold without a schema rebuild. It has `display_name='Deleted player'`, `display_name_key='deleted:<id>'`, a NULL `telegram_id`, `username`, `first_name` and `language_code`, `is_premium=0`, `public_boards=0`, and `deleted_at` set. Every board and public query excludes `deleted_at IS NOT NULL`.
  7. **Ban evasion:** if the player was banned, keep `ban_tombstones(identity_hash, banned_at, expires_at)`, where `identity_hash` = `SHA-256(PEPPER ‖ kind ‖ subject)`, for 180 days. Sign-up, Telegram log-in and linking check it. This is disclosed in the notice.
- **What we can't delete, and the notice says so:**
  - Analytics Engine events: pseudonymous `pid`, about 3 months of retention, no way to delete by key.
  - D1 backups: the `backup.yml` daily exports, kept for N days (the owner sets N, proposed 30).
  - Bot messages already delivered to the user's Telegram chat: the user can delete them in Telegram.
  - Cloudflare's own request logs.
- **Telegram-linked progress:** deletion removes the whole player, whatever log-in methods it has. A player who wants to keep their Telegram progress and only drop the web log-in uses **unlink** (§4), and the delete screen offers that as an alternative when two identities exist.

### 8. Privacy notice: outline (text for owner sign-off)
The page lives on the landing (`pixelarrow.app/privacy`, plus `/ru/privacy`; ADR-0007). It is linked from sign-up, Settings → Account, the delete screen and the landing footer.
1. **Who we are and how to contact us:** the controller, and a contact email for privacy requests.
2. **What we collect, by source:**
   - From Telegram: user id, first name, username, language, Premium flag (`initData`).
   - From you: email, password (stored only as a peppered hash), display name, clan names.
   - From play: game progress, items, ratings, battles.
   - Purchases: Telegram Stars charge ids, products, dates.
   - Technical: IP address (used transiently for rate limits and Turnstile, not stored with the account), device and browser family on the session list, crash reports, product analytics events (with the in-app opt-out).
3. **Why** (purpose and legal basis per category): running the account and the game (contract), security and abuse prevention (legitimate interest), bookkeeping for purchases (legal obligation), analytics (legitimate interest, with an opt-out).
4. **What is public:** display name, ranks, ratings, war standings, clan name and membership, shown in the game and on pixelarrow.app. How to hide yourself from the landing boards (`public_boards`).
5. **Processors and third parties:** Cloudflare (hosting, database, email sending, Turnstile bot checks), Telegram (platform and payments). No advertising, no data sales.
6. **Retention:** by category, as in §7 (active account; purchase records N years; backups N days; analytics about 3 months; ban hashes 180 days; email links 24 h or 30 min; sessions up to 30 days).
7. **Your rights:** access, correction (rename, change email), deletion (in-app, immediate), objecting to analytics (opt-out), complaint to a supervisory authority. Data export is handled by email request in v6 (an automated export is a proposal).
8. **Account deletion:** what is deleted, what is kept anonymised and why, and unlinking Telegram versus deleting.
9. **Children:** the minimum age (aligned with Telegram's terms; the owner confirms 13 or 16).
10. **Security:** in summary: hashed passwords, revocable sessions, verification emails.
11. **Changes to this notice,** the effective date, and the Russian translation (English prevails, or as the owner decides).

## Implementation Guidelines
- Must never merge game state between two players. Must resolve conflicts by keeping one and deleting the other.
- Must never let an account with purchases or entitlements be deleted through a conflict flow.
- Must require two-sided proof to link (the email link, or Mini App `initData` plus confirmation from the web session that created the code).
- Must require re-auth within 10 minutes for link, unlink, email change, conflict resolution and deletion.
- Must refuse to remove the last identity.
- Must keep the `players.telegram_id` mirror in the same batch as the telegram identity, and clear it on unlink and deletion.
- Must send a notice to the existing channels (email, bot) on every identity change.
- Must use `display_name` for everything public. Must never send `first_name`, `username` or `telegram_id` of another player to any client.
- Must validate display names and clan names on the server with the shared validator.
- Must classify every table that references a player in `DELETION_MAP`. A new table without a classification fails the deletion test.
- Must exclude `deleted_at IS NOT NULL` and `banned_at IS NOT NULL` from every leaderboard, and `public_boards = 0` from every public (landing) board.

## Alternatives Considered

### Alternative 1: Merge both accounts' progress
- **Pros:** nobody loses anything.
- **Cons:** about 45 tables with per-table rules (two wallets, two duel profiles, two season profiles in the same shard, two clans), duplication exploits (link, merge, unlink, repeat), and a huge test surface.
- **Rejection Reason:** risk and complexity far beyond the benefit while there are no users. "Keep one" is easy to explain and impossible to exploit.

### Alternative 2: Telegram Login Widget for web → Telegram linking
- **Pros:** a one-page flow without switching apps.
- **Cons:** needs BotFather `/setdomain`, a second hash scheme, and shows a Telegram pop-up that some browsers block. It also doesn't remove the need for the Mini App path in Telegram itself.
- **Rejection Reason:** the Mini App deep link reuses the verified `initData` check. Kept as a proposal for web log-in with Telegram.

### Alternative 3: Telegram first name as the default display name
- **Pros:** friendlier at first.
- **Cons:** it is exactly the personal-data exposure V6-011 removes, and real names aren't unique.
- **Rejection Reason:** V6-011.

### Alternative 4: A deletion grace period (30 days, then purge)
- **Pros:** recovers from mistakes and account theft.
- **Cons:** a second state for every board and query, a purge job, and the identities stay locked during the period.
- **Rejection Reason:** re-auth plus the typed confirmation is enough protection. Simpler to state in the notice. It can be added later.

### Alternative 5: Hard-delete the players row with cascades
- **Pros:** no tombstone.
- **Cons:** needs `ON DELETE CASCADE` or `SET NULL` on about 44 foreign keys (a table rebuild each), and would delete purchase records needed for bookkeeping and other players' battle history.
- **Rejection Reason:** a tombstone keeps integrity and the legal records with no personal data in them.

## Consequences

### Positive
- Players can move between Telegram and the web with one account and no exploit surface from merges.
- Public surfaces carry only a chosen, validated nickname.
- Deletion is real, complete, tested against the schema, and easy to explain.

### Negative
- When both accounts have progress, the player loses one of them (clearly shown, with confirmation).
- Linking web → Telegram needs a trip through the Telegram app and back.
- The generated default names are less personal until renamed.

## Risks
- **A new player-keyed table is added without a deletion rule.** Mitigation: the schema-driven deletion test fails until it is classified.
- **The blocklist misses abuse or blocks innocent names** (the Scunthorpe problem). Mitigation: a short list, admin rename with lock, and a history for review.
- **Code phishing:** an attacker sends a victim a `link_` deep link. Mitigation: the Mini App shows the target account's name and masked email, and the web side must confirm. The victim's Telegram can't attach to the attacker without the attacker confirming, and in that case the attacker gains only an empty or chosen account, with the victim warned by bot and email.
- **Deletion interrupted midway.** Mitigation: `deletion_jobs` plus idempotent steps, and the cron finishes them. The identities go in step 2, so the player is effectively gone at once.
- **Legal retention periods unknown.** Owner sign-off on the notice (owner action).

## Performance Implications
